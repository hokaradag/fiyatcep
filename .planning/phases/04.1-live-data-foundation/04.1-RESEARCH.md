**Researched:** 2026-04-01

## Summary

Phase 04.1 is a **spec-writing phase**, not a code-writing phase. Its deliverable is two committed files: `API-CONTRACT.md` (all endpoint definitions with JSON examples) and `DB-SCHEMA.sql` (CREATE TABLE statements). No production code is written or changed in this phase — the contract produced here governs Phases 04.2 and 04.3.

The locked decisions in CONTEXT.md fully specify the data model. The researcher's job is to audit the existing Flutter source code to extract every JSON field name, type, and nesting structure that the API must emit, so the planner can produce a complete, unambiguous contract rather than an incomplete sketch.

The only areas requiring judgment are: (1) how to model the `discounts` concept in the DB — dedicated table vs. view — and (2) whether to add optional pagination params to list endpoints.

**Primary recommendation:** Write the spec in a single focused session by reading Flutter models first, then deriving JSON shapes bottom-up, then writing DB tables that produce those shapes. This eliminates field-name mismatches between contract and implementation.

## Architecture Patterns

### Two-Tier Product Model (D-01, D-02)

The canonical product catalog decouples "what a product is" from "where it is sold and at what price":

```
products (canonical identity)
  id          TEXT PRIMARY KEY    -- internal only, never sent to Flutter
  name        TEXT                -- human-readable canonical name
  brand       TEXT
  category    TEXT
  normalized_name TEXT            -- lowercase, no diacritics, collapsed whitespace
  created_at  TEXT                -- ISO 8601 UTC

market_products (market-specific listing)
  id          TEXT PRIMARY KEY    -- THIS is ProductItem.id in Flutter
  product_id  TEXT REFERENCES products(id)
  market_id   TEXT REFERENCES markets(id)
  current_price REAL
  is_discounted INTEGER           -- SQLite boolean: 0 or 1
  last_scraped_at TEXT            -- ISO 8601 UTC
```

**Key insight for contract writers:** Flutter's `ProductItem.id` = `market_products.id`. The API returns `market_products.id` as the `"id"` field. The canonical `products.id` is an implementation detail of the backend join.

### Flutter Model → JSON Field Mapping (derived from source)

All field names below are extracted directly from the Freezed model source files. The `fromJson` generated code uses camelCase for JSON keys when the Dart field is camelCase, unless overridden by `@JsonKey`. These models have no `@JsonKey` overrides, so **JSON field names match Dart field names exactly**.

#### ProductItem JSON shape

```json
{
  "id": "mp-abc123",
  "marketId": "migros",
  "name": "Ayçiçek Yağı 1L",
  "brand": "Yudum",
  "market": "Migros",
  "price": 74.95,
  "isDiscounted": true,
  "priceHistory": [
    { "price": 76.50, "date": "2026-03-22T00:00:00.000Z" },
    { "price": 74.95, "date": "2026-03-28T00:00:00.000Z" }
  ]
}
```

Fields: `id` (String), `marketId` (String), `name` (String), `brand` (String), `market` (String), `price` (double), `isDiscounted` (bool), `priceHistory` (List, `@Default([])` — omit or send `[]`).

**`priceHistory` context:** For list endpoints (`GET /products`, `GET /products?marketId=...`), `priceHistory` should be embedded per market_product. For `GET /products/{id}`, `priceHistory` for that specific market_product is embedded. Sorted ascending by `recorded_at`.

#### PricePoint JSON shape

```json
{ "price": 76.50, "date": "2026-03-22T00:00:00.000Z" }
```

`date` is a `DateTime` in Dart. `json_serializable` 6.x serializes `DateTime` as ISO 8601 string. The Flutter model uses `DateTime.utc()` throughout — backend must emit UTC ISO 8601 (e.g., `"2026-03-22T00:00:00.000Z"` with trailing `Z`).

#### MarketPriceItem JSON shape (for `GET /products/{id}/prices`)

```json
{
  "marketId": "migros",
  "market": "Migros",
  "price": 79.90,
  "isDiscounted": false
}
```

Fields: `marketId` (String), `market` (String), `price` (double), `isDiscounted` (bool). No `id` field — this is a read-only aggregation result.

#### MarketItem JSON shape

```json
{
  "id": "migros",
  "name": "Migros",
  "description": "Türkiye'nin köklü süpermarket zinciri",
  "branchCount": 2500,
  "activeDiscountCount": 47,
  "supportsOnlineOrder": true,
  "hasLoyaltyProgram": true
}
```

Fields: `id` (String — the slug), `name` (String), `description` (String), `branchCount` (int), `activeDiscountCount` (int), `supportsOnlineOrder` (bool), `hasLoyaltyProgram` (bool).

**Note:** `activeDiscountCount` requires a live count query on the discounts table at read time, or a denormalized counter in the markets table updated on scrape.

#### DiscountItem JSON shape

```json
{
  "id": "d-xyz789",
  "productId": "mp-abc123",
  "marketId": "migros",
  "productName": "Ayçiçek Yağı 1L",
  "marketName": "Migros",
  "oldPrice": 79.90,
  "newPrice": 74.95,
  "validUntil": "2026-04-15T00:00:00.000Z",
  "note": "Haftalık indirim"
}
```

Fields: `id` (String), `productId` (String — maps to `market_products.id`), `marketId` (String — slug), `productName` (String), `marketName` (String), `oldPrice` (double), `newPrice` (double), `validUntil` (DateTime — UTC ISO 8601), `note` (String? — nullable, may be absent or null).

### API Response Envelope Pattern (D-10, locked)

All list endpoints:
```json
{ "data": [ ... ] }
```

Single-item endpoints (e.g., `GET /products/{id}`):
```json
{ "data": { ... } }
```

Error response:
```json
{ "error": { "message": "Not found", "code": "NOT_FOUND" } }
```

The Flutter `ApiClient` extracts `json['data']` in every `fromJson` callback. This pattern is already in production across all 3 remote datasource implementations. The contract must not deviate.

### Discounts DB Model (Claude's Discretion)

**Recommendation: Dedicated `discounts` table** (not a view over market_products).

Rationale:
- Discounts have their own lifecycle: `valid_until`, `old_price`, `new_price`, `note` — these are not derivable from market_products price history alone
- The scraper detects "is_discounted" state and captures both old and new price at scrape time; this needs its own row
- `DiscountItem.validUntil` requires an explicit expiry field — price_history has no expiry concept
- A view approach would require complex logic to infer old_price and valid_until from scrape artifacts

Recommended `discounts` table:
```sql
CREATE TABLE discounts (
  id TEXT PRIMARY KEY,
  market_product_id TEXT NOT NULL REFERENCES market_products(id),
  old_price REAL NOT NULL,
  new_price REAL NOT NULL,
  valid_until TEXT NOT NULL,  -- ISO 8601 UTC
  note TEXT,
  created_at TEXT NOT NULL,
  is_active INTEGER NOT NULL DEFAULT 1
);
```

`DiscountItem.productId` in Flutter = `market_products.id` (same as ProductItem.id).
`DiscountItem.productName` and `marketName` are JOIN fields from market_products + products + markets.

### Pagination (Claude's Discretion)

**Recommendation: Include optional `limit` and `offset` query params on list endpoints, but do NOT require them.**

Rationale:
- v1 REQUIREMENTS.md explicitly defers pagination to v2 (PERF-V2-01)
- Including optional params in the contract does not break v1 Flutter clients (unused params are ignored by Dio)
- Phase 04.2 backend can implement without pagination initially and add it in Phase 04.4 without a contract change
- Contract note: "Optional. If omitted, all records are returned."

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON field name mapping | Manual camelCase↔snake_case translation | Read Freezed model source directly | `json_serializable` uses Dart field names as JSON keys unless `@JsonKey` overrides exist — the Flutter models have NO `@JsonKey` overrides, so JSON keys ARE the Dart field names (camelCase) |
| DateTime serialization format | Custom date formatter | Document `json_serializable` default behavior | `json_serializable` 6.x produces/consumes ISO 8601 strings for DateTime. Flutter PricePoint uses `DateTime.utc()` — backend must emit UTC with Z suffix |
| Product identity across markets | Single products table with market column | Two-tier canonical product + market_products | Without normalization, same product appears as 6 independent rows with no cross-market linkage — breaks `GET /products/{id}/prices` entirely |

## Common Pitfalls

### Pitfall 1: JSON Key Case Mismatch

**What goes wrong:** Contract specifies `market_id` (snake_case), Flutter's `fromJson` expects `marketId` (camelCase). All deserialization silently returns null for those fields.

**Why it happens:** API designers default to snake_case (HTTP convention); Dart/Freezed uses camelCase. Without `@JsonKey`, `json_serializable` uses the Dart field name directly.

**How to avoid:** Verify EVERY field name by reading the actual Freezed `.dart` file (not the generated `.g.dart`). The Dart field name IS the JSON key. Confirmed: all Flutter models in this project use camelCase with no `@JsonKey` overrides.

**Warning signs:** All required fields deserialize to their default values (empty string, 0, false) after a successful HTTP 200.

### Pitfall 2: DateTime Format Missing UTC Marker

**What goes wrong:** Backend emits `"2026-03-22T00:00:00"` (no Z suffix). Flutter parses this as local time, not UTC. The `PricePoint` date arithmetic for time-range tabs (1H/1A/3A/1Y) produces wrong cutoffs.

**Why it happens:** Some backends omit the Z suffix from ISO 8601 strings. Dart's `DateTime.parse()` treats strings without Z as local time.

**How to avoid:** Contract must explicitly require UTC ISO 8601 with Z suffix: `"2026-03-22T00:00:00.000Z"`. Backend must call equivalent of Python's `datetime.utcnow().isoformat() + 'Z'` or use timezone-aware datetime with UTC.

**Warning signs:** Price history chart tabs show wrong date ranges, or all dates appear shifted by local timezone offset.

### Pitfall 3: GET /products/{id}/prices — Wrong ID Semantic

**What goes wrong:** Phase 04.2 developer assumes `{id}` in `GET /products/{id}/prices` is the canonical `products.id` and implements the lookup accordingly. Flutter sends `market_products.id` — backend returns 404 or wrong product.

**Why it happens:** The two-tier model creates two distinct ID namespaces. The endpoint description must be unambiguous.

**How to avoid:** API-CONTRACT.md must state explicitly: "The `{id}` parameter is `market_products.id` — the same value as `ProductItem.id` in Flutter. The backend resolves `products.id` internally via JOIN and returns prices for all `market_products` rows sharing that canonical product."

**Warning signs:** Cross-market price comparison shows only one market (the queried one) instead of all markets.

### Pitfall 4: priceHistory Missing on List Endpoints

**What goes wrong:** `GET /products` returns products without `priceHistory` (omitted for performance). Flutter's `ProductItem` has `@Default([])` so deserialization succeeds silently — but the price history chart shows no data.

**Why it happens:** Backend developer optimizes list endpoint by stripping nested data. D-11 explicitly requires `priceHistory` in list responses but this may be overlooked.

**How to avoid:** API-CONTRACT.md must show `priceHistory` array in the list endpoint response example, not just the detail endpoint. State explicitly: "priceHistory is embedded in ALL product responses."

**Warning signs:** Price history chart empty on products page but populated on product detail page (if different endpoints are used for each).

### Pitfall 5: activeDiscountCount Staleness

**What goes wrong:** `MarketItem.activeDiscountCount` returns 0 or stale count if computed from a static column that is not updated on scrape.

**Why it happens:** The field looks like a static attribute but is actually dynamic.

**How to avoid:** DB-SCHEMA.sql must either (a) specify this as a computed column (view/query at read time) or (b) note explicitly that the backend must UPDATE `markets.active_discount_count` after each scrape cycle. The contract should show the field but note its source.

## Open Questions

1. **`activeDiscountCount` source of truth**
   - What we know: `MarketItem.activeDiscountCount` is a required field in Flutter; it must be an integer in the API response
   - What's unclear: Should it be a denormalized column updated per scrape, or a live COUNT query on the discounts table?
   - Recommendation: Contract should specify it as a field in the response; DB-SCHEMA.sql should include it as a column in `markets` with a note that the scraper must update it. The live COUNT approach is simpler but adds latency to `GET /markets`. For v1 with daily scraping cadence, denormalized is fine.

2. **Price history embedding depth for list endpoints**
   - What we know: D-11 says `priceHistory` is included in product list responses; this is needed for the price chart on the products list page
   - What's unclear: How many history points to return in the list vs. detail endpoint? All points, or a capped number (e.g., last 90 days)?
   - Recommendation: Contract should specify "all available history points, sorted ascending by `recorded_at`". Phase 04.2 can add a cap if performance requires it — but this must be a contract revision, not a silent backend choice.

3. **`discounts` vs `market_products.is_discounted` relationship**
   - What we know: `market_products.is_discounted` is a boolean flag; `discounts` table stores discount details with `valid_until`, `old_price`, `new_price`
   - What's unclear: Should inserting a discount row automatically set `market_products.is_discounted = 1`, or should the flag be independent?
   - Recommendation: DB-SCHEMA.sql should note that `is_discounted` on `market_products` is the scraper's boolean flag (set at scrape time from retailer's data). The `discounts` table row provides the enriched details. They should be kept in sync by the scraper (not enforced by a DB trigger, to keep the schema simple for Phase 04.2).
