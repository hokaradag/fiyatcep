<decisions>
## Implementation Decisions

### Tech Stack
- **D-01:** Python backend — FastAPI framework, SQLAlchemy ORM, requests + BeautifulSoup for HTTP scraping. Lives in `backend/` subdirectory of the existing Flutter repo (same repository, different directory).
- **D-02:** Standard Python project structure: `backend/pyproject.toml` (or `requirements.txt`), `backend/app/` for application code, `backend/scraper/` for market scrapers.

### Database
- **D-03:** SQLite for Phase 04.2 — single-file database, zero infrastructure, embedded in process. DB file path: `backend/data/fiyatcep.db`. Schema tables match DB-SCHEMA.sql exactly (5 tables: products, markets, market_products, price_history, discounts).
- **D-04:** SQLite-compatible schema only (no Postgres-specific syntax). Migration path to PostgreSQL deferred — not needed for demo phase.

### Scraping Approach
- **D-05:** Migros first. Migros uses JSON-based internal endpoints on migros.com.tr — direct HTTP requests (no headless browser). Products fetched via internal API, parsed directly to ProductItem-compatible shape.
- **D-06:** Scraper outputs normalized product records: normalized_name (lowercase, remove diacritics, collapse whitespace) used for canonical product matching. Match logic: lookup `products.normalized_name` — insert new canonical product if no match, link to existing if match found.
- **D-07:** Each scrape run inserts one row into `price_history` per `market_product` record (even if price unchanged). `market_products.last_scraped_at` updated on every successful scrape.

### Scheduler
- **D-08:** APScheduler embedded in FastAPI — `AsyncIOScheduler` runs scrape jobs in-process. Daily refresh frequency (confirmed by REQUIREMENTS.md: "Türkiye'de market fiyatları günde en fazla bir kez değişir"). No external cron daemon needed for demo phase.
- **D-09:** Scheduler runs once on FastAPI startup, then on configured interval. Manual trigger endpoint (`POST /admin/scrape/run`) available for testing without waiting for schedule.

### Logging
- **D-10:** Structured scrape logging: each run records market, products_found, products_inserted, products_updated, prices_inserted, errors[], duration_ms. Written to `scrape_logs` table (extend schema) OR JSON log file — Claude's discretion which is simpler for Phase 04.2.
- **D-11:** Failed scrapes do not crash the scheduler — exceptions caught per-market, logged, retry on next scheduled run.

### Claude's Discretion
- Whether scrape logs go to a DB table vs a JSON file on disk (log file is simpler for demo phase)
- Exact Migros internal API endpoint discovery (may require inspecting network traffic from migros.com.tr)
- Retry logic details (immediate retry vs next-schedule retry)
- Whether to seed `markets` table from code or from a SQL seed file (seed file preferred for traceability)

</decisions>

### Established Patterns (from Flutter side, backend must match)
- JSON envelope: `{ "data": [...] }` for lists, `{ "data": {...} }` for single items — all Flutter remote datasources extract `json['data']`

<specifics>
## Specific Ideas

- Migros internal API: migros.com.tr loads product data via JSON endpoints (observable via browser DevTools Network tab). The scraper should target these endpoints rather than parsing HTML — faster, more stable, no headless browser needed.
- Canonical product matching at scrape-time: `normalized_name = name.lower().strip()` with Turkish diacritic removal (ğ→g, ş→s, ı→i, ö→o, ü→u, ç→c) + collapse whitespace. Then `SELECT id FROM products WHERE normalized_name = ? AND brand = ?`. This is already specified in Phase 04.1 specifics — implement exactly as described.
- `backend/` dir at repo root: `.gitignore` already exists; add Python-specific entries (`.venv/`, `__pycache__/`, `*.pyc`, `backend/data/*.db`).

</specifics>
