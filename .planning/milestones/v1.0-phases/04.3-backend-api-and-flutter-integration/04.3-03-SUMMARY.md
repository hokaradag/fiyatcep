## Decisions Made

- Price history chart empty state is expected: demo scrape volume produces only 1-2 price points per product; the 7d/30d/90d/365d range filters find zero points within those windows. The UI handles this correctly with a graceful message. Resolution: run scheduled scraper over time to accumulate history, or seed historical data before beta.
- Turkish character search issue is non-blocking: search normalization is applied to stored product names but not consistently to the query string in the Flutter TextField. Typing "süt" produces "st" (IME/keyboard interaction with TextEditingController). Tracked as a follow-up UX improvement. Fix: apply `TextNormalizer.normalize()` to the query string in `productsProvider` search filter before filtering products.
- Discounts table empty behavior is correct per spec: scraper sets `market_products.is_discounted` flag but does not write to `discounts` table, which requires separate lifecycle data (old_price, new_price, valid_until) not available from Migros search API.
- `backend/data/fiyatcep.db` is the authoritative DB path (SQLITE_URL = `sqlite:///./data/fiyatcep.db`); a stray `fiyatcep.db` at backend root should be gitignored.

## Issues Encountered

**Price History chart — low data volume (expected, non-blocking):**
- Backend `priceHistory` endpoint returns data correctly (verified in Task 1)
- Flutter `PriceHistoryChart` receives the array and applies date-range filters
- Demo scrape produces only 1-2 price points per product (scraped once), so all range filters (7d, 30d, 90d, 365d) find no points within the window
- Chart correctly shows "Seçilen aralıkta yeterli veri yok" — no crash, graceful UI
- Resolution: not a bug — will self-resolve as scheduled scraper accumulates history over time

**Turkish character search normalization (UX issue, non-blocking):**
- Typing "süt" in Products search TextField results in "st" being sent as query
- Searching "sut" does not match products named "süt"
- Root cause: `TextNormalizer.normalize()` is applied to stored product names but likely not to the incoming query string before filtering
- Secondary: Turkish IME keyboard may deliver decomposed Unicode to TextEditingController, further breaking normalization
- Impact: UX degradation for Turkish character searches only; non-Turkish searches work correctly
- Non-blocking for demo and beta milestones
- Follow-up fix: apply `TextNormalizer.normalize()` to query in `productsProvider` search filter
