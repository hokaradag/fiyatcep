<decisions>
## Implementation Decisions

### DB Schema Model
- **D-01:** Global canonical product catalog. Two-tier model: `products` table (canonical identity: id, name, brand, category, normalized_name) + `market_products` table (market-specific listings: id, product_id, market_id, current_price, is_discounted, last_scraped_at). Price history belongs to `market_products`, not `products`.
- **D-02:** Flutter's `ProductItem.id` maps to `market_products.id` — Flutter never sees the canonical `products.id`. The canonical product concept is internal to the backend only.
- **D-03:** `price_history` table: (id, market_product_id, price, recorded_at). One row per scrape event per market_product. Flutter's `PricePoint` maps to a price_history row.
- **D-04:** `markets` table: (id TEXT PRIMARY KEY using existing slug IDs, name, logo_url, banner_url, brand_color). Market slugs (migros, a101, bim, carrefoursa, sok, tarimkredi, filemarket) are canonical — already in Flutter's `marketBrands` map.

### Cross-Market Prices Endpoint
- **D-05:** New endpoint `GET /products/{id}/prices` returns `List<MarketPriceItem>` for a given `market_products.id`. Backend resolves the canonical `product_id` from `market_products`, then fetches current prices across all markets for that canonical product. Flutter does not need to know about canonical product IDs.
- **D-06:** New method `getProductPrices(String productId)` added to `ProductRemoteDataSource` abstract class and `ProductRemoteDataSourceImpl`. This is a Phase 04.3 implementation task — the interface addition is defined here in the contract.
- **D-07:** `productMarketPricesProvider` in `products_provider.dart` replaces its hardcoded `mockMarketPrices` call with `ref.watch(productRemoteDataSourceProvider).getProductPrices(productId)` in Phase 04.3.

### Deliverable Format
- **D-08:** Phase 04.1 produces two committed spec files in `.planning/phases/04.1-live-data-foundation/`:
  - `API-CONTRACT.md` — all endpoint definitions with request/response JSON examples
  - `DB-SCHEMA.sql` — CREATE TABLE statements for all tables
- **D-09:** These files are the frozen contract. Phase 04.2 implements the backend against DB-SCHEMA.sql. Phase 04.3 implements Flutter integration against API-CONTRACT.md. Neither phase changes the contract without explicit revision.

### API Response Format (Locked from existing code)
- **D-10:** All list endpoints use `{ "data": [...] }` envelope — already in all remote datasource implementations. Error responses use `{ "error": { "message": "...", "code": "..." } }`.
- **D-11:** `GET /products?marketId={slug}` for market-filtered products (already implemented in `ProductRemoteDataSourceImpl.getProductsByMarket`). ProductItem in the response always includes `priceHistory` for that market.

### Claude's Discretion
- Backend technology stack for Phase 04.2 (Python/FastAPI is a reasonable default given scraping is the primary workload, but not locked in this phase)
- Whether to include `discounts` in `DB-SCHEMA.sql` as a separate table or store as a view/query over `market_products`
- Pagination design (out of scope for v1 per REQUIREMENTS.md "Out of Scope" section, but may add offset/limit params to the contract as optional)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ApiClient` (`lib/core/network/api_client.dart`): Dio-based, handles `{ "data": [...] }` envelope extraction in `fromJson` callbacks. Phase 04.1 contract must match this exact format.
- All three remote datasource implementations: Already written and tested against the API contract shape — contract must not break their `fromJson` lambdas.
- Market slug IDs in `marketBrands` map: These are the canonical `markets.id` values — DB must use same slugs.

### Established Patterns
- API response envelope: `json['data']` extraction pattern used in all 3 remote datasources — contract locks this.
- Error envelope: `{ "error": { "message": "...", "code": "?" } }` — used in all `_handleDioException` methods.
- `DateTime` UTC for all dates: `PricePoint` uses `DateTime.utc()`, `DiscountItem.validUntil` is ISO 8601 — backend must emit UTC ISO 8601 strings.
- `isDiscounted` bool on both `ProductItem` and `MarketPriceItem` — backend price records must track this flag.

### Integration Points
- `productMarketPricesProvider` (`lib/features/products/presentation/providers/products_provider.dart`): Currently returns mock data directly — Phase 04.3 rewires this to call `getProductPrices()` on the remote datasource.
- `repository_providers.dart`: Single file where mock→remote swap happens for all 3 features — Phase 04.3 target.
- `api_client_provider.dart`: Base URL change point — placeholder `https://api.example.com/api/v1` replaced with real backend URL in Phase 04.3.

<specifics>
## Specific Ideas

- The `GET /products/{id}/prices` endpoint ID param is `market_products.id`, not `products.id` — this detail must be explicit in API-CONTRACT.md so Phase 04.2 implements the correct lookup.
- Price history response embedded in `GET /products/{id}` (and in product list items) — the `priceHistory` field in `ProductItem` is per-market, so it's already market_products-scoped. Backend returns `price_history` rows for that `market_products.id` sorted by `recorded_at` ascending.
- Matching strategy at scrape-time: normalize product name (lowercase, remove diacritics, collapse whitespace) + brand → lookup in `products.normalized_name`. If match found, link to existing canonical product. If not, insert new canonical product. This is Phase 04.2 implementation detail but the schema must support it (normalized_name column with index).

</specifics>
